# 3–5分钟 Demo 脚本

无需公网部署或API。直接在本地浏览器打开 [index.html](index.html)，GitHub阅读者可先看下方截图。所有对比页为**历史实验只读回放**，保留实际回答，非实时生成或伪造运行画面。原版产品UI截图来自运行中的V1.1已保存会话，没有新调用模型。

## 0:00–0:35 问题与职责

“我做的是企业制度查询助手。Baseline答案已经较准确，但引用准确率只有59.06%，确认11/80出现无依据业务推断。我的工作是需求与产品方案、评测集和Bad Case分析、治理优先级与验收，代码由AI Coding Agent辅助。”

## 0:35–1:20 场景1：正常查询

展示 [真实问答截图](screenshots/02_normal_query.jpg) → [展开来源](screenshots/02b_source_open.jpg)。指向北京550元、当前2026制度和模拟数据标记。说明原版UI与RAG来自AnythingLLM，不是个人重写。

## 1:20–2:15 场景2：来源噪声

打开 [B记录](baseline_noise.html) 和 [V1.1记录](v1_noise.html)，case DIRECT_ANSWER-01。答案都正确；B实际sources混入访客制度，V保留差旅制度。打开来源详情核对。不要将此讲成答案准确率提升。

## 2:15–3:15 场景3：无依据业务推断

打开 [B记录](baseline_inference.html) 和 [V1.1记录](v1_inference.html)，case UNSUPPORTED_INFERENCE-05。B把未提供的验收记录推断成缺少记录、暂不能付款；V把制度要求和无法确认的实际质量、材料及付款状态分开。逐字原回答在页面，不使用重写后的示范答案。

## 3:15–4:15 结果与失败

展示 [图表](../docs/assets/evaluation.svg)：引用127/128确认支持，另1待复核；正确拒答11/11。补充原V1曾因治理JSON异常中断，V1.1通过17/17离线故障注入，80题序列无服务级中断。

必须主动说明：2题治理失败；准确率退化；2例过度拒答；合成制度、单次固定回归、单评审初标，不能宣称“全指标提升”或生产可靠性。以FOLLOW_UP-08为例：对可回答的报销时限发生过度拒答。
